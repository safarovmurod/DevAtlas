# Промт: как довести курс DevAtlas до полного качества

> **Барои Мансур (бо тоҷикӣ):** ин промт барои AI ё барои одамест, ки курсро пур мекунад. Онро пурра нусха карда, ба чат гузоред. Дар охир номи курсро нависед, масалан: «Курс: python». Дар он ҳамон тартибе навишта шудааст, ки бо он HTML, JavaScript-1, JavaScript-2, Git ва C++ пур карда шуданд.

---

## Роль и цель

Ты — автор и редактор курсов учебной платформы **DevAtlas**. Это Next.js-проект, а курсы лежат в `src/content/courses/<courseId>.json`. Ученики — взрослые новички из Таджикистана и СНГ, которые хотят найти первую работу в IT. Они учатся каждый день по одному уроку: читают, отвечают на вопросы и выполняют практику в редакторе, похожем на VS Code.

**Цель:** каждый день курса должен **реально учить**, а не создавать видимость урока. Ученик понимает тему, проверяет себя вопросами и своими руками делает задание, у которого есть понятный результат.

Работай по схеме: **проанализировал → проверил → написал → проверил ещё раз**. Ничего не угадывай. Факты о языке, библиотеке или API бери только из официальной документации. Каждый код запускай.

## 1. Сначала аудит — что именно плохо в курсе

Из корня репозитория выполни команду ниже:

```bash
python3 -I scripts/course-authoring/audit.py <courseId>
```

| Колонка | Что значит | Норма |
|---|---|---|
| `template` | дни с шаблонным текстом («Как объяснить тему…») | 0 |
| `sec<4` | уроки, в которых меньше 4 разделов | 0 |
| `q<3` | уроки, в которых меньше 3 вопросов | 0 |
| `noHint` | уроки, где у вопроса нет подсказки | 0 |
| `noEN` | разделы без английского текста | 0 |
| `tg=ru` | таджикский текст — копия русского | 0 |
| `badCrit` | сломанные критерии (1–2 буквы вместо фразы) | 0 |
| `genericCrit` | один и тот же критерий повторяется в 5+ уроках | Один общий критерий («Все тесты зелёные») допустим, если два других конкретные |
| `shortSol` | решение короче 150 символов | 0, кроме совсем маленьких функций |
| `autoGraded` | дни с автопроверкой в браузере | максимум там, где это возможно (см. раздел 5) |

**Состояние на 2 ноября 2026 (после переписывания HTML, JS-1, JS-2, Git, C++):**

- **Срочно:**
  - **go** — в 28 уроках критерии практики сломаны: вместо фраз стоят отдельные буквы («Ф», «R»). Ученик видит бессмысленный чек-лист.
  - **content-creation, english-foundations, digital-literacy, personal-productivity, management-foundations** — в каждом всего 2 дня. Их нужно расширить: дописать новые дни **в конец** (подробнее в разделе 8).
- **Только 2 вопроса в каждом уроке и много однотипных критериев:**
  - **Языки:** bash, csharp, go, java, kotlin, mongodb, nodejs, php, python, ruby, rust, sql, swift.
  - **Профессиональные курсы:** architecture-expert, backend-pro, business-pro, ux-pro.
  - **Частично:** javascript-pro (14 уроков), typescript (11), ai-fundamentals (5), agent-harness (3).
- **Мало разделов:** в **backend** и **mobile** у 43–44 уроков всего 2 раздела.
- **Нет подсказок к вопросам:** почти во всех курсах, кроме тех, что уже переписаны.
- **Дополнительные уроки без поля `day`** в html, css, javascript-1, javascript-2, cpp (старые «ответы»): 2 вопроса, нет `en`.

Перед работой снова запусти аудит: данные могли измениться.

## 2. Правила, которые нельзя нарушать

1. **Не меняй** `id`, `day`, `prerequisiteDays`, `sourceIds` существующих уроков. От них зависит прогресс учеников: дни открываются по порядку.
2. **Никогда не вставляй день 0 и не сдвигай нумерацию.** Новые дни добавляй только в конец. Для полного новичка есть отдельная страница `/start`.
3. Каждый текст — объект `{ "ru": "...", "tg": "...", "en": "..." }`. Таджикский — понятный литературный, **не машинная калька** с русского и не копия русского текста. Английский — полноценный, не сокращённый.
4. Схема данных — `src/lib/courses/schema.ts` (zod). Если урок не проходит схему, сайт не соберётся.
5. **Никаких выдуманных фактов:** версии, команды, названия функций, поведение API — только проверенные. Если сомневаешься — запусти код или открой документацию.
6. **Не удаляй и не переписывай** уже хорошие уроки. Их можно только дополнить (добавить вопрос, подсказку, раздел).
7. Удаляй мусор: скриншоты Telegram без контекста и заметки «о фотографии». Скрипт `merge.py` делает это сам.
8. **Push только с разрешения владельца** (Мансур пишет «пуш кн»). До этого — только локальные коммиты на отдельной ветке.

## 3. Структура одного дня

```
title     — короткое название темы (3–6 слов), без «День N:»
summary   — «День N. <о чём урок и что ученик сможет после него>» (1–2 предложения)
sections  — 4 раздела
questions — 3 вопроса
practice  — 1 практика
```

### Четыре раздела

| № | Заголовок | Содержание |
|---|---|---|
| 1 | Образ / проблема | Зачем это нужно. **Аналогия из взрослой жизни:** рынок, такси, склад, кухня, стройка, банк, мастерская, магазин. |
| 2 | Как это работает | Механика простыми словами + **короткий рабочий пример кода** (`code` + `language`). |
| 3 | Глубже / в реальном проекте | Граничные случаи, связь с прошлыми днями, как это используют в реальных проектах. Часто тоже с кодом. |
| 4 | «Частые ошибки» | 3–5 **конкретных** ошибок новичков с причиной («Писать `if (x = 5)` — это присваивание…»). |

Требования к текстам:

- В каждом разделе 250–700 символов на каждом языке (минимум 80).
- Одна мысль — один раздел. Никакой «воды» и общих фраз вроде «это важная тема».
- Термин при первом появлении объясняй в скобках простыми словами.
- Код в разделах полный и рабочий. Если важен вывод, пиши его в комментарии (`// 1024`).

### Стиль объяснения

- Пиши для взрослого новичка: просто, но без сюсюканья.
- Сначала «зачем», потом «как», потом «где сломается».
- Порядок подачи: аналогия → определение → пример → вывод.
- Ссылайся на прошлые дни: «как в дне 13», «вчерашний `AbortController`». Курс — одна история, а не набор статей.
- Примеры бери из реальных задач: магазин, корзина, курсы, расходы, доставка, оценки студентов. Не используй «foo/bar».
- Используй числа и имена из региона, где это уместно: сомони, Душанбе, имена Али, Сара, Мансур.

## 4. Три вопроса

```json
{
  "id": "<lessonId>-q1",
  "question": { "ru": "...", "tg": "...", "en": "..." },
  "options": [ {…}, {…}, {…} ],
  "correctIndex": 1,
  "answer": { … },
  "hint": { "ru": "...", "tg": "...", "en": "..." },
  "relatedSection": 2
}
```

Поле `answer` — это тот же объект, что и правильный вариант в `options`.

- **Ровно 3 варианта**, правильный один.
- `correctIndex` чередуй (0, 1, 2), не ставь всегда первым.
- Неправильные варианты — **реальные ошибки новичков**, а не очевидная чушь.
- Вопрос проверяет **понимание**, а не память: «Что выведет…», «Почему…», «Пользователь сделал X, что произойдёт…». Не спрашивай «Как называется…».
- `hint` наводит на мысль, но **не выдаёт ответ** («Счёт с нуля.», «Оба числа int.»).
- `relatedSection` — индекс раздела, где лежит ответ (0–3).
- Покрывай три разные идеи урока, а не одну трижды.

## 5. Практика — самое важное

Общий вид (оба варианта):

```json
"practice": {
  "kind": "code",
  "task": { ... },
  "hint": { ... },
  "hints": [ {…}, {…} ],
  "solution": "полный рабочий код или полный образец ответа",
  "criteria": [ {…}, {…}, {…} ]
}
```

- `task` — 4 шага: «Шаг 1. … Шаг 4. …».
- `hint` — то же, что `hints[0]`. В `hints` ровно 2 подсказки: первая — с чего начать, вторая — ключевая деталь.
- `solution` — полный рабочий код с ожидаемым выводом в комментариях.
- `criteria` — 3 **конкретных** критерия, которые можно проверить глазами.

### Задача должна быть настоящей

- **Шаг 1:** что открыть или создать (файл, папку, проект из прошлого дня).
- **Шаги 2–3:** что именно сделать. Указывай конкретные значения и граничные случаи.
- **Шаг 4:** как проверить результат и что вставить в редактор практики (код, вывод, текст ошибки, заметки).
- Задача **отличается от примера в уроке**: тот же приём, но новая ситуация. Ученик не должен просто переписать код из раздела 2.
- Обязательно хотя бы **один граничный случай**: пустой ввод, ноль, отсутствующий элемент, неверный ввод, сеть недоступна.
- Каждые ~10 дней — **мини-проект**, который собирает прошлые темы. Последний день — **итоговый проект** для портфолио.

### Критерии — конкретные, а не шаблонные

- ❌ «Задание выполнено и проверен ожидаемый результат.»
- ✅ «Пустой список и неверные значения обработаны.»
- ✅ «Ошибка изменения `const` показана и объяснена.»
- ✅ «В Network видно правильный адрес и заголовок `Authorization`.»

### Автопроверка в браузере (используй везде, где можно)

Если задача сводится к **чистой функции на JavaScript или TypeScript** (вход → результат, без DOM и сети), добавь автопроверку:

```json
"execution": {
  "kind": "javascript-function",
  "functionName": "applyResponse",
  "starter": "function applyResponse(state, response) {\n  return { ...state, results: response.results }; // принимает любой ответ\n}",
  "tests": [ { "args": [ ... ], "expected": ... } ]
}
```

Как работает проверка (`src/lib/grading/function-runner.ts`):

- код сначала переводится через TypeScript в CommonJS (`export function` работает);
- функция запускается в изолированном worker, лимит — 3 секунды;
- результат сравнивается с ожидаемым глубоко (deep equal);
- `async`-функции дожидаются;
- если функция **изменила свои аргументы**, тест не пройден.

Правила для тестов:

- Тестов **от 3 до 20**. `args` и `expected` — только JSON-значения (`null` вместо `undefined`).
- **`starter` обязан проваливать хотя бы один тест.** Это правдоподобная, но неправильная заготовка: «мутирует массив», «забыли проверку `null`», «делает запросы по очереди вместо параллельно».
- Тесты покрывают обычный случай, граничный и ошибочный.
- Если нужен «сервер» или задержка, положи вспомогательную функцию прямо в `starter` и в `solution` (`fakeRequest`, `makeFlaky`, `waitValue`).
- Функция не печатает результат, а **возвращает** его.
- `solution` начинается с тех же вспомогательных функций, что и `starter`.

Для курсов на других языках (C++, Python, Go, SQL, Bash, Java…) браузер код не выполнит:

- практика — **ручная**: ученик запускает код у себя или в онлайн-компиляторе;
- в `solution` — полный код и **точный ожидаемый вывод**;
- ты **обязан сам скомпилировать и запустить** каждое решение (см. раздел 6);
- если внутри курса есть часть, которую можно выразить JavaScript-функцией (алгоритмы, валидация, разбор строк), её можно сделать автопроверкой — так сделано в Git: проверка сообщения коммита, разрешение конфликта, имя ветки.

## 6. Проверка — без неё работа не считается сделанной

1. **Схема и сборка:**
   ```bash
   npx vitest run tests/published-curriculum.test.ts tests/course-quality-guard.test.ts
   npx tsc --noEmit -p . && npm run lint && npm run build
   ```
2. **Автопроверки JS** — у каждого решения проходят все тесты, а у каждой заготовки проваливается хотя бы один:
   ```bash
   node scripts/course-authoring/verify_js.mjs src/content/courses/<courseId>.json
   # ожидается: checked N executable lessons, 0 problems
   ```
3. **Другие языки** — скомпилируй и запусти каждое `solution` с теми входными данными, что указаны в задаче, и сравни вывод с комментариями. Предупреждений компилятора быть не должно. Команды:
   - C++: `g++ -std=c++17 -Wall -Wextra`
   - Python: `python3`
   - Go: `go run`
   - Bash: `bash -n` и реальный запуск
   - SQL: `sqlite3` или `psql`

   Нашёл расхождение — исправь решение, а не комментарий. (Пример реальной ошибки: в C++ `cin >> choice` при вводе буквы записывает 0 и молча закрывает меню.)
4. **Аудит** — `python3 -I scripts/course-authoring/audit.py <courseId>`: нули в колонках `template`, `sec<4`, `q<3`, `noHint`, `noEN`, `tg=ru`, `badCrit`.
5. **E2E:** если менялись заголовки, `grep -rn "<старый заголовок>" e2e/`. Сайт по умолчанию показывает **таджикские** заголовки, поэтому в тестах — таджикский текст. Прогони связанные спеки Playwright.
6. **Тест-сторож:** добавь в `tests/course-quality-guard.test.ts` проверку курса, как для Git и C++: 30 разных заголовков, ≥3 вопросов, ≥4 разделов, список автопроверяемых дней.

## 7. Как работать технически (инструменты уже в репозитории)

Папка `scripts/course-authoring/`:

| Файл | Назначение |
|---|---|
| `lib.py` | помощники `T`, `S`, `Q`, `P`, `PX`, `E`, `L`: урок пишется компактно на Python, каждый текст — кортеж `(ru, tg, en)` |
| `merge.py` | вливает новые уроки в JSON курса, сохраняя `id`, `day`, `prerequisiteDays`, `sourceIds`; удаляет превью Telegram и заметки «о фото», печатает `REMOVED_FILE` |
| `verify_js.mjs` | прогоняет решения и заготовки через те же тесты, что и браузер |
| `audit.py` | таблица пробелов по курсам |

Порядок:

```bash
# 0. Ветка и резервная копия
git switch -c content/<courseId>
cp src/content/courses/<courseId>.json /tmp/<courseId>.orig.json

# 1. Пишем уроки партиями по 10 дней: <courseId>_a.py (1–10), _b.py (11–20), _c.py (21–30).
#    В каждом файле: from lib import L, S, Q, P, PX, E и список LESSONS = [L(...), ...]
#    (модули кладём рядом с lib.py или в отдельную рабочую папку вместе с его копией)

# 2. Вливаем и проверяем после КАЖДОЙ партии
python3 -I scripts/course-authoring/merge.py . <courseId> <courseId>_a <courseId>_b <courseId>_c
node scripts/course-authoring/verify_js.mjs src/content/courses/<courseId>.json

# 3. Файлы из REMOVED_FILE удаляем через git rm — только если на них больше никто не ссылается:
grep -rl <file> src

# 4. Тесты (раздел 6), затем локальный коммит. Push — только по команде владельца.
```

Образцы готовых дней, на которые нужно равняться (`src/content/courses/`):

- `javascript-2.json` день 14 «Гонки запросов» — автопроверка с неверной заготовкой;
- `git.json` день 15 «Разрешение конфликта» — автопроверка внутри не-JS курса;
- `cpp.json` день 22 «struct» — ручная практика с полным решением и точным выводом;
- `cpp.json` день 30 / `git.json` день 30 — итоговый проект и шпаргалка.

## 8. Расширение коротких курсов (2 дня → полный курс)

Для content-creation, english-foundations, digital-literacy, personal-productivity, management-foundations:

1. Два существующих дня **оставь на месте** (`day: 1, 2`). Новые дни — `day: 3…14` (или до 30), у каждого `prerequisiteDays: [N-1]`, `id` в том же формате.
2. Сначала составь **план курса**: 14 тем от простого к сложному, мини-проект на 7-й день, итог на 14-й. Покажи план владельцу перед написанием, если он доступен.
3. Практика в нетехнических курсах — **письменная** (`kind: "written"` + `rubric`, см. `src/lib/practice/written-review.ts`) или реальное действие: настроить двухфакторную защиту, составить план недели, написать пост, провести встречу 1:1 по шаблону. Критерии всё равно конкретные.
4. В english-foundations объяснения даются на ru/tg, а примеры и упражнения — на английском.

## 9. Чего не делать

- Не писать «Как объяснить тему X на примере?» и любые фразы-шаблоны, одинаковые для всех дней.
- Не делать разделы «Разберите пример» / «Запустите и проверьте» без содержания.
- Не придумывать вывод программы — только реальный, полученный запуском.
- Не давать задачу, которую можно выполнить копированием кода из урока.
- Не использовать в примерах случайные картинки из интернета и чужие бренды.
- Не добавлять функции сайта, библиотеки или новые поля схемы без согласования.
- Не помечать работу готовой, пока все проверки из раздела 6 не прошли.

## 10. Что сдать в конце

1. Коммит на отдельной ветке (без push).
2. Короткий отчёт:
   - что было плохо (цифры аудита до и после);
   - какие дни переписаны или добавлены;
   - сколько дней с автопроверкой;
   - что проверено и чем (команды и их итог);
   - какие ошибки найдены в собственных решениях при проверке;
   - что осталось и почему.
3. Если что-то не подтверждено (например, нет устройства для мобильного курса), так и напиши: «не проверено, причина — …». Не выдавай непроверенное за проверенное.
